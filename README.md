# 找回消失的垃圾桶

市政 debug松 題目 #2。用人流、店家與市民通報，算出台北哪裡最缺垃圾桶、該用哪種方式處理，並公開增設進度。

台北行人專用垃圾桶從全盛時期近 3,000 組，縮減到約 800 組。這個網站回答三個問題：哪裡最缺？為什麼？市府做到哪裡了？

## 功能

| 分頁 | 做什麼 |
| --- | --- |
| 缺垃圾桶指數 | 六角網格依「缺桶指數」上色。市民視角只看到六個故事與開關；政府單位視角另外可調權重、上限、新增指標，公式即時顯示，點一格看逐項計算；列出建議增設前 30 名 |
| 垃圾桶填滿度 | 假設每個桶都是智慧垃圾桶，顯示此刻的填滿 %。市民：用目前位置、捷運站或路名找附近還有空位的垃圾桶。政府單位：右側表格列出所有桶的填滿、電量、廠牌、贊助商，可篩選需清運、低電量並排序；附一週「固定排程 vs 感測派車」比較 |
| 市民通報 | 點地圖通報亂丟垃圾、垃圾桶滿溢、家戶垃圾棄置；每格依通報量給出「增設／加強清運／加強取締」建議 |
| 施政進度 | 30 個建議點的設置狀態、更新日期與負責清潔隊，可依行政區篩選 |

畫面右上角可以切換「市民／政府單位」兩種視角（沒有登入，只是展示用）。

## 資料來源：真實 vs 模擬

捷運、公車、YouBike、飲料店與餐飲店都是**真實開放資料**，於 2026-10-19 從臺北市資料大平臺下載一次（不會自動更新）。網頁上每個圖層與數字旁都會標示「真實資料」或「模擬資料」，旁邊的「!」滑鼠移上去（手機點一下）會顯示資料來源網址或模擬方法（內容在 `web/public/data/sources.json`，由 `pipeline/02_simulate.py` 產生）。原始檔與下載方式見 [`data/NOTES.md`](data/NOTES.md)。

| 資料 | 現況 | 來源／說明 |
| --- | --- | --- |
| 捷運站與人流 | 真實 | 捷運公司車站資料（74 站座標）＋各站分時進出量（2026 年 9 月，每日平均） |
| 公車站牌 | 真實 | 交通局公運處臺北市公車站牌位置圖（3,407 個站位） |
| YouBike 站點 | 真實 | 交通局 YouBike2.0 即時資訊的站點快照（1,792 站） |
| 飲料店 | 真實 | 環保局飲料杯空杯回收點（1,392 家門市，未參加回收的飲料店不在內） |
| 餐飲店（含小吃） | 真實 | 產業局「設址臺北市所營事業含餐館業清冊」（20,285 家，商業登記資料） |
| 行人專用垃圾桶 | 真實 | 環保局「行人專用清潔箱總表」（[開放資料](https://data.gov.tw/dataset/121355)），681 處。環保局正式名稱為「行人專用清潔箱」，網站統一叫垃圾桶。注意：檔案裡沒有北投區、南港區只有 4 處，總數也少於環保局 2026 年 8 月議會報告的 806 組 |
| 住宅區 | 真實 | 民政局臺北市門牌位置數值資料（2026-10-02 版，1,157,763 筆門牌；每層樓一筆，接近戶數），在瀏覽器裡串流彙總成 100 公尺方格（`data/raw/addresses_100m.csv`）。台北住商混合，商圈裡也住很多人，所以：住宅值＝住家門牌（門牌－店家）×（1－商圈程度），商圈程度看飲料店、餐飲店、捷運人流（各以第 90 百分位為滿）與夜市／攤販集中場 300 m 內；住宅值未滿 100 的格子不算。共 1,212 格 |
| 歷史市民通報 | 模擬 | 店家多、附近沒有桶的地方較常出現 |
| 智慧垃圾桶填滿紀錄 | 模擬 | 主辦說明此資料不存在；時段曲線用捷運真實分時人流 |
| 智慧垃圾桶設備資料 | 模擬 | 電量、廠牌、贊助商；廠牌與贊助商為虛構名稱 |
| 增設進度 | 模擬 | 預設指標下的建議前 30 名，以固定亂數種子指定狀態（`web/src/lib/progress.ts`） |

所有模擬都固定 `seed=42`，每次產生的結果相同。網頁上使用者新增的通報只存在該瀏覽器的 localStorage，不收集任何個資。

## 演算法

全台北切成尖頂朝北的正六角形網格：中心到頂點 150 公尺（約步行 3 分鐘），每格約 0.06 km²。有任何資料點的格子約 2,100 格（`web/src/lib/hexgrid.ts`；`pipeline/hexgrid.py` 是同一套，有測試確保格子編號一致）。

**每一格只看格內的資料，不看鄰格。**計算全部在瀏覽器裡（`web/src/lib/indicators.ts`），使用者可以即時調整：

```text
每個指標的分數 = min(格內數值 ÷ 上限, 1)        → 所有指標都在 0～1，影響力只由權重決定
缺桶指數     = Σ(需要桶的權重 × 分數) − Σ(不缺桶的權重 × 分數)，低於 0 算 0
上限預設     = 有資料的格子中，第 90 百分位的數值（可手動改）
```

預設指標就是展示用的六個故事（`web/src/lib/stories.ts`），每個都可以用開關暫時不算（保留權重）。捷運人流不放進預設：搭捷運的人和逛商圈、買飲料的人大多是同一群，一起算會重複計算。

| 故事 | 指標 | 圖層 | 格內怎麼算 | 方向 | 預設權重 |
| --- | --- | --- | --- | --- | --- |
| 1 逛街吃完東西找不到垃圾桶 | 飲料店（商圈） | 飲料店 | 有幾家 | ＋ 需要桶 | 0.20 |
| 2 YouBike 菜籃裡塞滿垃圾 | YouBike 站 | YouBike | 有幾站 | ＋ | 0.10 |
| 3 住宅區有人丟家用垃圾 | 住宅區 | 住宅區 | 「住宅值」（商圈打折後的住家門牌） | － 不缺桶 | 0.20 |
| 4 等公車時垃圾沒地方丟 | 公車站 | 公車站 | 有幾站 | ＋ | 0.20 |
| 5 市民通報過這裡很髒 | 市民通報 | 通報（含使用者新增） | 有幾件 | ＋ | 0.15 |
| 6 這裡已經有垃圾桶 | 現有垃圾桶 | 垃圾桶 | 有幾個 | － | 0.40 |

政府單位視角可以再用現有圖層新增指標，例如餐飲店數量、捷運站數（站內有垃圾桶，扣分）、現有桶填滿速度。

公車站權重較高，依據是環保局過去的垃圾桶設置作業程序：優先設在公車站牌多的地點。

**分級**（地圖顏色）：依缺桶指數佔「需要桶權重合計」的比例，0 為不缺，未滿 15% 還夠用、15–30% 有點缺、30–45% 缺、45% 以上很缺。

**建議增設點**：依缺桶指數由高到低挑選，彼此不相鄰，取前 30 名。

**匯入資料**：使用者可以上傳 CSV（每列一個地點，要有緯度、經度欄位；名稱與數值欄位會自動辨識），選圖示與顏色後變成新圖層，並可直接新增「格內有幾個」或「某欄位加總」的指標。檔案只在瀏覽器裡讀取，存在該瀏覽器的 localStorage，不會上傳（`web/src/lib/csv.ts`）。

**市民通報的處置建議**（同一格內）：通報 3 件以上時，沒有桶 → 增設；有桶且每桶一週滿溢 10 小時以上 → 提高清運頻率或改用智慧桶；有桶但不常滿 → 加強巡邏與取締。

**垃圾桶填滿度**：「即時」＝把現在的台北星期幾、幾點對應到一週模擬的同一個小時，採用 B 感測派車的結果。每小時增加量＝桶的填滿速度 × 時段係數（捷運分時曲線）× 週末係數＋雜訊。A 固定排程每天 06:00、14:00、22:00 清空；B 感測派車填到 80% 就派車、下一小時清空。模擬結果（真實垃圾桶位置）：滿溢 11,342 → 422 桶時，出車 14,301 → 10,768 次。

## 如果市府上任 100 天內要落地

| 期間 | 主責局處 | 做什麼 |
| --- | --- | --- |
| 第 1–30 天 | 環保局、資訊局 | 開放垃圾桶裁撤紀錄與違規棄置資料，換成真實資料，確定權重 |
| 第 31–60 天 | 環保局、區清潔隊 | 選 2 個行政區試點：建議前 30 點會勘、增設；50 個桶裝填滿感測器 |
| 第 61–100 天 | 研考會（1999） | 通報整合進陳情系統，由環保局每週更新施政進度頁 |

成本粗估（新聞報導數字）：北市一組行人垃圾桶設置成本約 1.2 萬元，增設 30 組約 36 萬元；桃園智慧垃圾桶感應模組年租金約 4 萬元，50 組約每年 200 萬元。

## 專案結構

```text
pipeline/        Python：把原始資料算成靜態 JSON（只需要跑一次）
  01_load.py       讀 data/raw/ 的真實資料
  02_simulate.py   補齊模擬資料
  03_grid.py       整理點位 → pois.geojson、bins.geojson 等
  hexgrid.py       自訂正六角形網格
  04_fill_sim.py   填滿模擬 → fill.json
  05_smart_bins.py 智慧垃圾桶電量、廠牌、贊助商 → smart_bins.json
web/             Vite + React + TypeScript + Leaflet：讀 JSON、畫地圖
  src/lib/indicators.ts  圖層、指標、缺桶指數、建議點
  src/lib/progress.ts    施政進度（模擬）
  src/tabs/        四個分頁
data/raw/        原始下載檔（不進 git）
```

## 部署

網站部署在 **Cloudflare Workers**（純靜態網站，沒有後端），並用 **Cloudflare Access** 限制只有團隊成員能看（登入時寄 email 驗證碼）。

- Cloudflare 連接這個 GitHub repo，push 到 `main` 後自動 build 與部署；其他分支會產生預覽網址。
- **分支預覽**：Settings → Builds → Previews Base 的 Preview command 是 `npx wrangler preview`，`web/wrangler.jsonc` 必須有 `"previews": {}` 區塊（可以是空的）。每個分支的預覽網址是 `https://<分支名稱，斜線換成 ->-taipei-trash-can.sage-otomo.workers.dev`，例如 `feat/rename-terms` → `feat-rename-terms-taipei-trash-can.sage-otomo.workers.dev`。
- Cloudflare 會在分支第一次 build 時，從 Previews Base 複製一份設定給這個分支，之後改 Previews Base 不會同步到已經存在的分支。舊分支的指令不對時，最簡單的做法是開一個新分支名稱重新 push。
- Build 設定：Root directory `web`、Build command `npm run build`、Deploy command `npx wrangler deploy`。
- 要上傳哪些檔案寫在 `web/wrangler.jsonc`（`dist/`），裡面的 `name` 必須和 Cloudflare 後台的 Worker 名稱相同。
- GitHub Actions（`.github/workflows/ci.yml`）只負責跑測試與確認可以 build。

**比賽當天提交前**：到 Worker 的 Settings → Domains & Routes，把 Cloudflare Access 關掉，網站才會公開，評審與投票者才看得到。
